# ADR 012 — Transaction-local row policies and separate runtime roles

Date: October 15, 2026. Status: implemented and locally verified on PostgreSQL 18.6.

Application filters remain necessary, but an accidentally unscoped SQL query should not read every tenant. Migration 0005 enables and forces row-level security on all eight tenant-data tables. Both read visibility and write checks require a nonempty transaction-local `atlas.tenant`. Membership visibility instead requires the verified issuer and subject context, allowing a user to select among their own workspaces. Missing context denies access. SQLite receives the revision marker but has no row policies.

Tenant-facing store, upload, job, retrieval and membership operations establish context with parameterized `set_config(..., true)` inside their transaction. Commit and rollback reset that context before a pooled connection is reused. Context comes from authenticated identity or the verified subject, never the request body's claimed tenant. Explicit tenant predicates remain in the queries.

The API must connect as a nonowner, nonsuperuser, NOBYPASSRLS role with no schema CREATE privilege or membership in elevated roles. Startup rejects violations. The trusted worker has a different nonsuperuser BYPASSRLS login because it must claim jobs across tenants. Its grants omit membership access and UPDATE on reviews; API grants omit membership writes, audit updates, destructive table operations and DDL. The worker is a privileged trusted component, not an untrusted agent sandbox. `deployment/postgres-runtime-roles.sql` is a provisioning reference; the equivalent privileges were exercised with disposable real SCRAM logins. The reference file has not been applied to a deployment and intentionally contains no passwords.

Startup verifies forced flags, exactly one expected all-command/public policy per protected table, and the normalized read/write predicates. Missing, weakened or extra permissive policies fail startup. Migration connections set `row_security=off`: this does not grant bypass, but prevents a filtered data check from silently treating hidden rows as absent. Production migration credentials and procedures remain operator responsibilities.

Real local tests exercise unfiltered reads, rejected cross-tenant writes, empty context, commit/rollback pool reuse, persistent vector access under restricted credentials, issuer/subject membership isolation, revocation, forbidden grants, role escalation, policy drift, and API submission with publication by a separate worker login. The suite uses real logins, not administrator sessions that merely SET ROLE. All 17 PostgreSQL groups passed. The local SQLite demo upgraded from 0004 to 0005 with all nine existing data tables unchanged against pre-upgrade hashes and a consistent private backup.

Limits: a trusted application role can itself set these custom PostgreSQL settings. This protects against omitted filters and context leaks; it does not authenticate JWTs inside PostgreSQL or contain a compromised application credential capable of arbitrary SQL. Superusers and BYPASSRLS roles bypass policies. Unique/foreign-key checks can also reveal constraint-level information, so RLS is not a proof against all database side channels. Deployment TLS, credential management/rotation, network isolation, audited operator identity, backup restore under production roles, load testing and live cloud validation remain pending.

Semantics follow PostgreSQL's [row-security documentation](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) and [transaction-local configuration functions](https://www.postgresql.org/docs/18/functions-admin.html). Policy-expression normalization is checked against the tested server; upgrades must rerun the compatibility suite rather than assume identical introspection formatting.
