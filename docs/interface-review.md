# Review interface

ATLAS uses a quiet document layout: warm paper, dark text, a serif face for requirements and source excerpts, and compact navigation. Counts share one strip rather than four separate cards. Status colors identify evidence, conflicts and gaps; they do not decorate the page. The selected requirement keeps a visible edge and readable text.

CHAOSLAB uses the same application shell with a restrained blue section rule and aligned numeric summaries. Failed cases and incomplete runs remain visible. Its tables and scope notes carry the detail; the interface adds no new performance claims. The recorded viewer now describes the saved reviews directly instead of opening with a slogan. The fictional public lab keeps its separate session and input restrictions.

The refinement also removes decorative navigation symbols, the redundant pipeline-step chips and the engineering-status footer. The exact execution mode remains beside the source record, where it helps a reviewer understand the result. Navigation exposes its current page to assistive technology, and the sign-in page uses a properly centered layout. System fonts avoid another external request or font dependency.

## First visit

The first interface assumed familiarity with procurement terms. The lab now explains the buyer/supplier problem before starting, defines RFP in context and keeps a short worked example visible after analysis. The example button opens the actual recovery requirement and its eight-hour supplier excerpt. Finding help separates a missing excerpt from proof of missing capability. Source hashes and character offsets sit behind a disclosure; the highlighted passage stays primary. The action appears before the detailed guide on narrow screens.

This follows progressive disclosure, recognition over recall and a concrete task sequence. These are design choices, not a claim of measured usability. Three existing Chromium workflows now also check the context, real example selection and restored guidance. All three passed, along with the native suite (833 passed, eighteen optional database groups skipped). ## Reading the evaluator

CHAOSLAB now starts with the question its measurements answer: how do we know the review is right? The overview defines the task and links directly to comparison, misleading-evidence and recovery sections. Metric definitions sit behind an optional disclosure. The baseline/model comparison remains visible; the longer fault, database and retrieval tables are grouped under “View failed cases and technical checks.” Section links open that group when needed. Recorded model runs are labeled as recorded, including incomplete runs and unknown cost. No measured values changed.

Nineteen local Chromium cases passed, including phone/tablet checks before and after expanding details. [Evidence](../reports/evaluation-guide.json), [phone overview](../reports/evaluation-guide-390.png) and [tablet overview](../reports/evaluation-guide-900.png). These checks establish working navigation and layout, not proven comprehension by new visitors.
