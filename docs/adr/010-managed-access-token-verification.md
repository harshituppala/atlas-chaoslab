# ADR 010 — Explicit managed access-token trust

Date: October 15, 2026. Status: optional managed API authentication and server-owned memberships implemented; live provider validation pending.

Public deployment must replace the development bearer-token map. The first boundary is an independently testable resource-access-token verifier, not a login UI or an assumption that any signed JWT grants access.

The operator pins an HTTPS issuer, resource audience and HTTPS public-key endpoint. RS256 with explicit `at+jwt` or `application/at+jwt` type is the supported profile. ID tokens, algorithm substitution, token-supplied key URLs/material, critical extensions, ambiguous duplicate JSON members and oversized input are rejected. Signature, issuer, single resource audience, required expiry/issue time, optional not-before and bounded subject are verified. NumericDate values must be integers. Only issuer, subject and expiry cross this boundary; caller-supplied tenant/role claims grant no permission.

Public keys must be RSA 2048–4096 bits, exponent 65537, with distinct bounded IDs and no private fields. The configured endpoint is fetched without bearer credentials, redirects, ambient proxy settings or compressed responses. The response budget is 64 KiB/16 keys. Network operations have a three-second per-operation timeout and a total elapsed-time check between chunks; a stalled read can add one timeout beyond that elapsed budget. A 300-second key cache and a shared ten-second refresh gate bound arbitrary unknown-key and signature-failure refreshes. Concurrent cold requests share one fetch. Key rotation replaces the full cache; an outage never extends hard expiry. Known keys remain usable within their existing TTL. Invalid credentials and unavailable trusted keys are separate exceptions; both fail closed.

Offline tests execute real RSA signatures against a controlled HTTP transport, including altered issuer/audience/times, ID-token type, forged role claims, algorithm confusion, invalid key sets, signature replacement, rotation, outages, duplicate claims and concurrent fetches. These are not live identity-provider tests. Managed API mode now uses the verifier plus a server-owned membership registry. Local bearer credentials have no fallback in this mode. A workspace selector is accepted only against active membership; ambiguous selection and unknown/revoked membership fail with 403. Each request rereads membership, so revocation applies on its next authorization check. In-flight requests are not canceled by revocation. The registry supports compare-and-swap changes with atomic audit recording through a trusted private-file operator CLI; no public self-enrollment route exists. Migration 0004 refuses to discard registry data on downgrade. The demo remains local bearer authentication. Production operator attribution/least-privilege database roles, browser login flow and real provider validation remain required.

The strict access-token profile follows [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html). Library verification behavior follows the [PyJWT API](https://pyjwt.readthedocs.io/en/stable/api.html). Cognito and other providers with different access-token profiles need an explicit separate reviewed configuration; this does not claim universal OIDC compatibility.
